3．同一個程式，解 5 張迷宮（含從未見過的）

AlphaDev 只在左邊 3 張迷宮上搜尋，卻發現了能直接解右邊 2 張從未見過的迷宮的程式。 這說明它找到的是通用邏輯，不是記憶解法。

訓練迷宮（已見過）×3 測試迷宮（從未見過）×2
類比真實 AlphaDev： 論文中，AlphaDev 的排序程式是在特定輸入分布上搜尋，但最終驗證在所有可能的輸入組合上都正確排序。 它不是「記住了怎麼排某些數字」，而是發現了一個通用的排序演算法。

5. 三個論文核心技術細節

對應 PPT Slide 4 / 6 / 8——比 Demo 更深一層，讓報告更完整。

A State St = Pt（程式）+ Zt（執行狀態）

迷宮 Demo 的 state 只有「目前位置」；真實 AlphaDev 的 state 有兩個部分：目前已寫的指令序列 Pt，加上把這段程式跑在所有測試輸入後的 register/memory 狀態 Zt。兩部分各自送給不同的 encoder 處理。

Pt — 目前程式指令

↓ Transformer Encoder
程式語法結構的 embedding
+
Zt — 跑在測試輸入後的狀態
輸入 [3,1,2] → %eax=3, %ecx=1…
輸入 [2,3,1] → %eax=2, %ecx=3…
輸入 [1,2,3] → %eax=1, %ecx=2…
↓ CPU State MLP
執行效果的 embedding
↓ 兩個 embedding 合併 → AlphaDev 完整 state representation → Policy + Value 預測
為什麼需要 Zt？ 光知道程式長什麼樣（Pt）不夠——兩段不同的指令序列可能讓 %eax 都等於 3，但對 %ecx 影響完全不同，下一步要加什麼指令也就不同。Zt 讓 agent 知道「程式跑起來做了什麼」，才能做出正確決策。
B MCTS 由神經網路引導——不是隨機嘗試

神經網路對每個 state 同時輸出兩個預測：Policy π（下一條指令選哪個的機率分布）和 Value V（從此 state 出發預計能得到多少 reward）。MCTS 用兩個信號做 UCB/PUCT 計算，把搜尋資源集中在「機率高且預期 reward 高」的分支。

和迷宮 Demo 的 cross-entropy 搜尋差在哪？ Cross-entropy 是「採樣一批程式，保留高分的，更新採樣分布」——每次都要跑完整個程式才能評分。 MCTS 則是「在搜尋樹上逐步展開，用 V 提前判斷一段 partial program 的前景」——不需要等程式寫完就能決定要不要繼續。在 1014+ 的空間裡，這個差異非常關鍵。
C Dual-Head Value Network — 為什麼要兩個 value head？

對固定排序（Sort3/4/5）：code 長度和 latency 高度相關，單一 reward 夠用。 但對可變排序（VarSort）：程式需要 branching（分支），code 長度和實際 latency 不相關——更長的程式有時跑更快，因為避免了代價高的分支跳轉。需要兩個獨立的 value head 分開預測。
